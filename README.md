# 本地设备配置协调组件（Go）

用本地存储模拟"设备端 + 期望配置面"，演示一个声明式配置协调（reconcile）循环：
期望配置发生 创建 / 更新 / 删除 后，设备实际状态最终与期望一致；
设备被手动改动（漂移）会在下一轮被纠正回来；删除必须等设备清理动作完成才算结束。

整个组件不依赖任何外部服务，全部并发安全，可用 `go test -race` 验证。

## 目录结构

| 路径 | 职责 |
| --- | --- |
| `internal/domain` | 领域模型：期望配置、设备状态、事件、协调结果、动作记账、可分类错误 |
| `internal/store` | 本地存储：`DesiredStore`（期望配置/墓碑）、`DeviceStore`（模拟设备端，支持故障注入与手动篡改） |
| `internal/reconcile` | 协调引擎：收敛、漂移纠正、删除清理、并发单飞、事件幂等、错误分类与退避重试 |
| `cmd/demo` | 端到端可运行演示 |

## 协调语义

### 1. 声明式收敛（创建 / 更新）

- 每个事件携带生产端按因果序分配的、**按设备单调递增的 `Revision`**（资源版本）。
- 协调器把期望写入 `DesiredStore`，随后比较设备实际状态：
  - 设备缺失 / 版本落后 → 调用 `Apply` 下发（记账 `Apply`）。
  - 版本相同但内容不同（被手动改过）→ 调用 `Apply` 纠正（记账 `Drift`）。
  - 版本与内容都一致 → 已收敛，**不动作、不记账**。
- `Resync()` 对期望存储中的所有对象跑一轮再同步，用于纠正手动漂移、补做未完成的删除。

> 为什么版本号由事件携带，而不是处理时自增？
> 并发下多个工作单元抢锁的顺序是随机的。若在"处理时刻"分配版本，晚到的旧事件会拿到更大的
> 版本号并覆盖新内容（出现"版本号最新、内容却是旧的"）。因此版本必须代表**事件的因果序**：
> 协调只向最高 `Revision` 收敛，乱序/迟到的旧版本事件不会覆盖新版本
> （`DesiredStore.Put` 返回 `ErrStaleRevision`，协调器转而向当前最新期望收敛）。

### 2. 漂移纠正

设备版本号没变、但配置内容被外部手动改动时，下一轮 `HandleEvent` 或 `Resync` 会检测到
"同版本、内容不一致"，以 `Drift` 动作把设备纠正回期望，且只在真正纠正时记一次账。

### 3. 删除（两段式，清理完成才算结束）

1. `Delete` 事件先把期望对象置为 `Deleting`，**保留墓碑**（不立即移除）。
2. 对设备执行 `Cleanup`；只有清理成功后才 `Purge` 移除墓碑。
   - 清理遇到瞬时故障会退避重试；在此期间墓碑一直存在，事件不丢。
   - 删除一个不存在的对象、或墓碑已在但设备已清理，都按幂等成功处理。
3. 删除事件同样携带 `Revision`：迟到的旧删除不会删掉更新版本的配置。

## 并发协调与幂等

- **同一事件单飞（single-flight）**：相同 `EventID` 被并发投递时，只有一个真正执行，
  其余等待并共享同一结果；设备不会被重复下发。
- **事件结果缓存**：相同 `EventID` 重复投递（即使间隔很久）直接回放首次结果，
  与"只处理一次"完全一致。瞬时失败不缓存（需要靠重试/再投递推进）。
- **每设备分片锁**：同一设备的协调动作严格串行（不同设备可并行），
  因此"事件处理"与"再同步"、"多个事件"之间不会互相覆盖。
- **记账只在成功动作时发生**：失败的尝试、已收敛的空转都不记账，杜绝重复记账。
  通过 `Reconciler.Ledger(deviceID)` 可查看 `Apply / Drift / Clean` 动作序列。

## 重试与错误分类

设备端错误统一为 `domain.ReconcileError`，用 `Transient` 布尔区分两类，
在对外结果 `domain.Result.Status` 中也必须能区分：

| 类别 | 例子 | 处理方式 | 结果状态 |
| --- | --- | --- | --- |
| 瞬时失败 `Transient=true` | 临时锁定 `ErrLocked`、短暂不可用 `ErrUnavail` | 指数退避（`BaseDelay` 翻倍、上限 `MaxDelay`）重试，**事件不丢**；超过 `MaxAttempts` 或 ctx 取消时交还调用方，稍后再投递 / `Resync` 即可继续推进 | `StatusTransient` |
| 永久失败 `Transient=false` | 字段非法 `InvalidField`、参数越界 `OutOfRange`、缺字段 `MissingField` | **立即停止重试**，不触设备、不落期望版本，记录明确原因 | `StatusTerminal` + `TerminalReason` + `TerminalMessage` |

- 退避等待通过 `Sleeper` 接口抽象，测试用假睡眠器立即推进，真实运行用定时器，
  且等待期间响应 `context.Context` 取消。
- 参数静态校验（`deviceID` 非空、`Revision>0`、`config` 非空、`vlan∈[1,4094] 整数`）
  在触达设备前完成，违规即永久失败。
- 永久失败结论按"设备 + 期望版本"缓存：同一版本重复事件不再触设备；
  当更新版本的 `Upsert` 到来时，旧结论自动失效。

## 本地验证

要求 Go 1.25+。

```bash
# 1. 端到端演示：创建、幂等、更新、漂移纠正、删除清理、瞬时重试、永久失败
go run ./cmd/demo

# 2. 全部单元测试（含数据竞争检测）
go test -race ./...

# 3. 查看每个用例的“触发条件 / 判定依据”日志
go test -race ./... -v

# 4. 静态检查
go vet ./...
```

### 测试覆盖

- **正常路径**：创建收敛、更新到新版本、删除清理完成、删除不存在对象幂等。
- **并发协调**：同一事件并发单飞；同设备多版本事件 + 重复投递并发（最终必为最高版本、
  下发版本严格单调不重复不回退）；不同设备并发互不阻塞；删除与再同步并发无悬挂中间态。
- **重复事件**：相同 `EventID` 串行/并发重复投递，结果一致、设备只下发一次、不重复记账。
- **漂移纠正**：手动篡改后 `Resync` 纠正回期望并记一次 `Drift`，第二轮无动作。
- **删除清理**：清理成功后才移除墓碑；清理瞬时故障退避重试；重复删除不重复清理。
- **错误分类**：瞬时失败退避重试直至成功 / 超过上限返回可区分的 `Transient`；
  永久失败立即 `Terminal` 且不触设备；新版本清除旧的永久失败结论。

每个用例在开头用 `t.Logf` 打印"触发条件"与"判定依据"，`go test -v` 时可见。
