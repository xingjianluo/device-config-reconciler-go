# device-config-reconciler-go（本地设备配置协调组件）

一个纯本地、零外部依赖的设备配置协调（reconciliation）组件：用内存存储模拟设备端，
把"期望配置"持续收敛到"设备实际状态"，并在重复事件、并发处理、漂移、删除清理以及
瞬时/永久两类失败下给出可预期的行为。面向线上流量形态，还支持高频乱序更新收敛、
删除与重建交错、批量下发的容量控制与背压。

## 目录结构

```
internal/
  model/       领域类型：期望配置、设备状态、事件、动作、账本、结果、错误分类
  classify/    错误分类：TRANSIENT（瞬时，可重试） vs PERMANENT（永久，不重试）
  storage/     并发安全的内存存储：期望配置 + 按对象的代际（generation）账本 + 最近结果
  device/      设备模拟器：本地 map 存实际状态，可注入瞬时/永久故障，带下发计数器
  reconciler/  协调核心：逐对象加锁、代际防回退、比对期望与实际、下发/纠正/清理、幂等记账
  worker/      事件队列与工作器：并发执行、事件去重、按对象合并、有界队列与背压、
               指数退避重试、积压统计
cmd/demo/      端到端演示
```

## 协调语义（Reconciliation Semantics）

对象身份为 `deviceID/feature`，每个对象有一个期望配置（带单调递增的 `generation`）
和一份设备实际状态。协调器对事件的处理：

- **PUT（创建/更新）**：先持久化期望配置，再让设备收敛到该期望。
  - 设备无状态 → 下发 `CREATE`；设备有状态但与期望不一致（漂移）→ 下发 `UPDATE`。
  - 目标代际已是账本最后一条且设备状态与期望一致 → 返回 `NONE` 空操作，不下发。
  - **乱序保护**：到达的 PUT 代际低于已存期望代际时，绝不覆盖期望、绝不把设备
    拉回旧值；而是改为向最新已知代际重新收敛（见下文"乱序收敛"）。
- **DELETE（删除）**：删除必须**等清理动作真正完成**才算结束。
  - 先移除期望配置；设备上仍有状态时下发 `CLEANUP`。
  - `CLEANUP` 成功后才清除设备状态与代际账本并报告 `Converged=true`。
  - 清理失败时删除保持"未完成"，重复投递 DELETE 会继续重试清理；完成后的重复
    DELETE 是幂等空操作。
- **RESYNC（周期/触发再对账）**：重新读取期望与实际，被手动改动过的设备会在下一轮
  被纠正回期望值（漂移纠正）；无漂移时不产生任何下发，也不重复记账。

### 幂等（Idempotency）

幂等由两层保证，重复投递的结果与"只投递一次"完全一致：

1. **工作器层（事件去重）**：相同 `EventID` 只被接受一次（`seen` 集合）；同一对象已有
   事件在队列/处理中时，新事件进入按对象的合并槽（见下文"合并"），不叠加队列项。
2. **协调器层（代际记账）**：每个对象一把互斥锁，同一对象串行处理，不同对象并行；
   成功下发后该 `generation` 在账本中只记录一次。重复处理同代际且设备已一致时直接
   空操作，因此不会重复下发、重复记账或互相覆盖。

## 高频乱序更新下的收敛

上游控制面短时间内对同一对象连续提交多次变更，且因网络抖动/重放/重试，到达顺序
不保证等于提交顺序。收敛规则：

- **代际即提交顺序**：PUT 事件携带的 `generation` 单调递增，是"最后一次提交"的
  唯一依据，与到达先后无关。
- **迟到旧变更不回退**：到达的 PUT 代际 < 已存期望代际时，期望配置不被覆盖，设备
  不会被拉回旧值；该次处理结果标记为已收敛并注明
  `stale PUT gen=X superseded by gen=Y`。
- **迟到旧变更不丢弃**：旧 PUT 到达时会改为向**最新已知代际**重新驱动一次收敛。
  若最新代际的下发此前因瞬时故障尚未成功，这次"多余的"收敛会把它补上，对象不会
  卡在中间值。
- **重复变更零副作用**：同 `EventID` 在工作器层去重；同代际重复处理在协调器层
  空操作；并发下同一把对象锁保证同一条变更不会被重复下发到设备。
- **合并不改收敛结果**：工作器合并槽对 PUT 保留**最高代际**（而不是最晚到达），
  因此乱序到达时最新提交也不会被旧事件顶掉。

**兼容范围**：乱序保证覆盖 PUT（配置变更）之间，以 `generation` 为依据；DELETE 不
携带代际，DELETE 与 PUT 的先后以**到达顺序**为准（控制面需按提交顺序投递删除/
重建序列，本地队列按对象串行处理，保证到达序即处理序）。

## 删除与重建交错

删除流程与新的创建/更新交错时的语义：

- **删除未确认前不宣称结束**：清理动作（`CLEANUP`）未成功前，对外结果始终
  `Converged=false`，设备状态保留；只有清理确认完成才报告删除结束。
- **删除过程中来了创建/更新**：最后一次提交的意图获胜。新的 PUT 会按最新期望直接
  收敛（设备状态被更新为新期望，不残留中间态），此前未完成的删除被自然取代。
- **删除紧跟创建**：同一对象上 PUT → DELETE 连续到达时，队列按对象串行处理，
  最终设备上不留任何状态、账本清空。
- **一串事件结束后结果唯一**：无论中间交错多少步，最终状态只取决于最后一次提交
  的意图——最后是删除则设备无任何残留；最后是创建/更新则设备精确等于最新期望。

## 批量下发、容量与背压

- **有限并发**：`Config.Workers` 限制同时处理的对象数，可一次提交大量对象，
  工作器池并行消费。
- **有界队列**：`Config.MaxQueueSize > 0` 时，队列中的等待事件数不超过该上限；
  满员时 `Submit` 返回 `ErrQueueFull`（背压信号），事件**未被接受**（`EventID`
  也不会被标记为已见），调用方降速后可直接重投。`MaxQueueSize = 0`（默认）保持
  原有的不限长行为，向后兼容。
- **按对象合并**：同一对象已有事件在队列/处理/重试中时，新事件进入该对象的
  合并槽（最多 1 个），不占用队列项、不受队列满员拒绝；N 次连续变更对队列的
  占用是 O(1)。合并槽被占满时按"取代规则"取舍：PUT 之间保留**最高代际**，
  不同类型事件（PUT/DELETE）之间保留**最晚到达**；被取代的事件其意图已被
  存活事件覆盖，不会导致对象卡在中间态。
- **积压可观测**：`Stats()` 返回 `{Queued, Inflight, Retrying, Coalesced}` 四项
  计数——队列等待数、有未完成工作的对象数、退避重试中的事件数、合并槽中的
  事件数，可用于发现积压；`Drain()` 后全部归零。

## 重试与错误分类规则

设备错误先经 `internal/classify` 分类，两类失败在对外结果 `ActionResult.ErrClass`
中明确区分：

| 类别 | 触发场景（示例） | 处理方式 | 对外表现 |
|------|------------------|----------|----------|
| `TRANSIENT` | 设备临时锁定、短暂不可用、超时、未知错误（fail-closed） | 事件保留，按指数退避重试，直到成功或达到 `MaxRetries` | 重试期间不丢事件；成功后收敛。重试耗尽仍是 `TRANSIENT`，不会被误判成永久失败 |
| `PERMANENT` | 字段非法（mode 非 auto/manual）、参数越界（level 不在 [0,100]）、设备明确拒绝载荷 | 第 1 次即停止重试 | `Converged=false`、`ErrClass=PERMANENT`、`Reason` 写明原因；非法载荷不会下发到设备 |

- 未知/未分类错误默认按 `TRANSIENT` 处理（fail-closed），避免意外错误静默丢事件。
- 退避：`BaseBackoff * 2^(attempt-1)`，上限 `MaxBackoff`；重试次数上限 `MaxRetries`。
- 非法字段在协调器本地即被判为 PERMANENT，不会产生任何设备操作。

```bash

# 4. 覆盖率

# 5. 端到端演示：创建/更新/重复事件/漂移纠正/瞬时重试/永久失败/删除清理/
```

### 测试覆盖的场景

- **并发协调**：64 个 goroutine 同时处理同一对象，断言恰有 1 次 CREATE、账本长度为 1、
  所有结果收敛；50 个不同对象并行收敛互不串扰（`-race` 下运行）。
- **重复事件**：同一 `EventID` 从多 goroutine 投递 100 次，断言只有一个收敛结果、
  账本只有一条；同一事件在协调器层直接处理 5 次结果等价于 1 次。
- **漂移纠正**：先收敛，再在设备上"手动改坏"，RESYNC 后断言设备被纠正回期望；
  无漂移的再次 RESYNC 不下发、不记账。
- **删除清理**：清理受永久/瞬时故障阻断时删除不算完成、设备状态保留；设备恢复或
  重试成功后才清除状态与账本；完成后重复 DELETE 幂等。
- **乱序收敛**：代际 [5 3 1 4 2 5 3 1] 乱序+重复到达，断言设备水位单调不回退、
  最终停在 gen5、账本只有一条；最新代际下发失败时迟到的旧 PUT 会把收敛补到最新
  代际而不是自己的载荷；30 代 x3 重复并发乱序洪泛下最终收敛到 gen30、账本短且
  严格递增、设备下发次数有界。
- **删除与重建交错**：DELETE 清理被瞬时故障挂起时来了 PUT gen2，断言删除未被提前
  宣称完成、最终设备精确等于 gen2 期望；PUT→DELETE→PUT 背靠背提交后最终是
  重建结果；PUT→DELETE 背靠背提交后设备无任何残留。
- **批量与背压**：容量为 2 的队列灌入 5 个新对象，断言 2 接受 / 3 返回
  `ErrQueueFull` 且拒绝不标记 `EventID`（降速后可重投成功）；对在途对象的提交走
  合并槽不占队列；设备锁定期间对同一对象连发 50 次变更，断言合并槽恰为 1、
  设备下发次数 ≤5、最终收敛到最后一代；`Stats()` 在积压期间可见 Queued/Retrying
  计数、`Drain()` 后全部归零。
- **正常与异常路径**：瞬时故障退避重试后成功（attempts 计数）、重试耗尽仍标记
  TRANSIENT；非法字段一次即停并带明确 PERMANENT 原因。

单测日志会打印每条断言的**触发条件（trigger）**与**判定依据（verdict）**，
可用 `go test -v` 查看，例如：

```
trigger=PUT generations arrive out of order [5 3 1 4 2 5 3 1] (gen5 committed last) | verdict: device converges to gen5 and never regresses
verdict: final device level=50, desired gen=5, ledger=1 -> converged to last commit -> PASS
```
